# Deploying with Supabase (database) + Render (hosting)

This project's database layer is plain PostgreSQL via Prisma, so it works
with Supabase's free Postgres out of the box — no code changes needed
beyond what's already in `prisma/schema.prisma`.

## 1. Create the Supabase project

1. Go to [supabase.com](https://supabase.com) → **New project**.
2. Pick a name (e.g. `srems`), a strong database password (save it), and a
   region close to your Render region (e.g. `oregon` on Render → pick a US
   region on Supabase).
3. Wait ~2 minutes for the project to finish provisioning.

## 2. Get your two connection strings

In Supabase: **Project Settings → Database → Connection string**.

You need **both**:

| Use | Where in Supabase UI | Port | Env var |
|---|---|---|---|
| App runtime (pooled, serverless-friendly) | "Connection pooling" tab, mode = Transaction | `6543` | `DATABASE_URL` |
| Migrations only (direct connection) | "Connection string" tab | `5432` | `DIRECT_URL` |

Copy each, substitute your real password, and append
`?pgbouncer=true&connection_limit=1` to the **pooled** one only:

```
DATABASE_URL="postgresql://postgres.xxxx:PASSWORD@aws-0-REGION.pooler.supabase.com:6543/postgres?pgbouncer=true&connection_limit=1"
DIRECT_URL="postgresql://postgres.xxxx:PASSWORD@aws-0-REGION.pooler.supabase.com:5432/postgres"
```

Put these in your local `.env` for now (copy `.env.example` → `.env` first).

## 3. Push the schema & seed data to Supabase

```bash
npm install
npx prisma db push                    # creates all tables in Supabase
npm run db:seed                       # optional: loads sample accounts + 100 properties (flats, land, plots)
```

Open the Supabase **Table Editor** afterwards — you should see `users`,
`profiles`, `properties`, `bookings`, etc. already populated.

## 4. Deploy the app on Render

`render.yaml` in this repo is already wired for this setup (Render hosts
the Next.js app; Supabase hosts the database — no Render Postgres is
provisioned).

1. Push this repo to GitHub.
2. On [render.com](https://render.com): **New → Blueprint**, point it at
   your repo. Render will read `render.yaml` automatically.
3. Render will create one web service (`srems`). Before the first deploy,
   open its **Environment** tab and set:
   - `DATABASE_URL` → the pooled Supabase string from step 2
   - `DIRECT_URL` → the direct Supabase string from step 2
   - `APP_URL` → your Render URL, e.g. `https://srems.onrender.com`
   - `EMAIL_USER` / `EMAIL_PASSWORD` → your SMTP credentials (Gmail App
     Password works well) — optional; without these, verification/reset
     emails just get logged to the server console instead of sent.
   - `JWT_SECRET` is auto-generated by Render, you don't need to set it.
4. Trigger the deploy. Render's build command
   (`npm install && npx prisma db push --accept-data-loss && npm run build`)
   pushes the schema straight to Supabase, then builds the app. `db push`
   is used instead of `migrate deploy` because this repo doesn't ship a
   `prisma/migrations` history — `db push` syncs the schema directly and
   needs no migration files, which is why the app failed to find any
   tables on the previous Render deploy.

## 5. Sanity check

Once deployed, visit `https://<your-app>.onrender.com`, sign up, and
confirm the new user shows up in Supabase's **Table Editor → users**.

## Notes

- Free-tier Supabase projects pause after a week of inactivity — the
  first request after a pause will be slow while it wakes up.
- Never commit `.env` — only `.env.example` should be in git.
- If `prisma db push` fails on Render with a prepared-statement error,
  double check `DATABASE_URL` has `pgbouncer=true&connection_limit=1` and
  that `DIRECT_URL` points at the port-`5432` (non-pooled) string.
